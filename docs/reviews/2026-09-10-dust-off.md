# Dust-off remediation — 2026-09-10

Branch: `codex/dust-off-fixes`. Four Astra agents reviewed and remediated the
project, followed by another bug review and a separate performance review.
No production database was modified. No changes were pushed.

## Remediation

- Isolate scheduler integration tests in disposable PostgreSQL containers; never
  use ambient production credentials.
- Build separate discrete futures chains per symbol, order by delivery date,
  resolve archived RICs, reject incomplete chains, and report failed extraction.
- Preserve cache failures and inclusive request bounds; track successful fetch
  ranges rather than equating a MIN/MAX envelope with complete history.
- Coordinate shared LSEG session ownership and serialize shared client access.
- Restore PostgreSQL-backed Parquet export for all data shapes, retain timestamps,
  isolate intraday intervals, safely encode filenames, and atomically replace data
  files. Export full stored histories to avoid truncating older yearly partitions.
- Restrict credential file/directory permissions, encode database credentials
  correctly, validate app-config shape, and exclude secrets from Docker contexts.
- Use transaction-local PostgreSQL staging tables rather than shared tables.
- Run typechecking with installed runtime dependencies. Fix dictionary-row handling
  in instrument resolution, extraction progress, and conversion-factor retrieval.
- Correct scheduler timezone and weekday presets, retention defaults, transaction
  rollback behavior, and reject nonpositive chunk sizes.
- Pin registry-verified CI image digests; refresh them manually after review.

## Performance review

- Scheduler existing-instrument lookup: one parameterized batch query rather than
  one query per symbol. Regression proves **200 SELECT calls become 1**. A synthetic
  1 ms/query simulation measured median **290.727 ms → 1.597 ms**; this is **not** a
  live database latency result.
- Prediction-market candles: one cursor / `executemany` dispatch instead of one
  cursor / execute per row. A 200-row regression checks parameter order and values.
- Persistent cache coverage avoids repeated unknown-calendar history fetches.
- Bounded synthetic rolling: 43,200 input rows, 20 contracts and 19 rolls
  processed in 0.103 seconds. A 100,000-row Parquet export took 0.015 seconds.
  These samples are not production throughput guarantees.
- Writer `iterrows` / whole-frame buffering remains a profiling candidate, not an
  asserted production bottleneck. No speculative serializer rewrite was made.

## Deployment and data follow-up

1. Apply the normal `init_db` schema initialization/migration to create the new
   `fetch_coverage` table before using the updated cache. Back up and review the
   target configuration first; this review did not run it against a live database.
2. Audit existing persisted scheduler cron strings. Old numeric weekday presets
   must be explicitly migrated to named weekdays; changing source defaults does
   not rewrite existing database jobs. See `docs/SCHEDULER.md`.
3. If rows are manually deleted, invalidate their associated fetch coverage too.
   Provider-request coverage is not independent proof of every expected bar; use
   an instrument calendar/timestamp provider for that stronger check.
4. Audit/rebuild previously generated continuous futures histories separately.
   Fixes prevent new defects; they do not repair stored historical outputs.
5. Run disposable database integration tests with a Docker daemon available.
   Docker was installed but no daemon was reachable in this review environment.
6. Bloomberg remains unvalidated. Fixed-day / expiry-driven pipeline rolling is
   rejected until authoritative expiry metadata is supplied, rather than guessing
   expiries from the end of a bounded response.
